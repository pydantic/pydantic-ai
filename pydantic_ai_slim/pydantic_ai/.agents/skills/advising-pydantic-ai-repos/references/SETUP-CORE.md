# SETUP: core Pydantic AI

Patterns a repo hand-rolls that the installed `pydantic-ai` already ships. Each min version applies to the package
it names: a row can name a `pydantic-ai` part and a `pydantic-ai-harness` part, and each is gated on that package's
installed version. A part applies when its package is at or above its min version; below it, report it as an UPGRADE
finding instead. A Harness part on a repo without Harness is an optional addition.

| id | hand-rolled shape | detection signal | adopt instead (API + min version) | why | caveats | confidence | docs |
|---|---|---|---|---|---|---|---|
| S-FALLBACK | Run-level fallback: `try: agent.run(...) except ...: agent.run(..., model=other)`, or a loop over a model list around the run | `except` around `.run(`/`.run_sync(`/`.iter(` that re-calls with a different `model=`; lists of model names iterated around a run | `ModelFallback` capability (2.64.0) for provider and transport errors; `SelectModel` keyed on the output retry count, `ctx.retry` (2.60.0) for rejected outputs | Falls back per request, so completed tool calls and the request budget survive; a restarted run redoes side effects and gets a fresh budget | Usage-limit errors must never fall back (a fallback that catches `UsageLimitExceeded` doubles spend); keep a run-level loop only to switch to a different agent, not a different model | high | https://pydantic.dev/docs/ai/capabilities/model-fallback/ |
| S-RETRY-PARTS | Detecting tool errors with `isinstance(part, RetryPromptPart)` in scorers, dashboards or trace processing | `RetryPromptPart` in `isinstance` checks or part-kind comparisons | `is_retry(part)` (2.69.0) | Since 2.60.0 a tool retry is recorded as `ToolReturnPart(outcome='retried')`, and a retry that answers no tool call (output validator or `ModelRetry` feedback) as `RetryFeedbackPart`, so the old check silently finds nothing and failed tool calls and rejected outputs look like successes | None: this is a correctness fix. On 2.60.0 to 2.68.x, check `isinstance(part, RetryFeedbackPart) or (isinstance(part, ToolReturnPart) and part.outcome == 'retried')`, which is what `is_retry` matches | high | https://pydantic.dev/docs/ai/core-concepts/retries/ |
| S-OUTPUT-CHECK | Output checked after the run: code inspects `result.output` and raises or drops bad results (ids not in the run's data, missing evidence), so the model never gets a chance to fix them | `agent.run(...)` followed by `if`/`raise` on `result.output` fields; membership checks of returned ids against data the run had | `@agent.output_validator` raising `ModelRetry` (2.0.0); for values that must come from a run-time set, `Choices(...)` (2.46.0); for tool arguments, `args_validator` (2.0.0) | The model sees why its answer was rejected and retries within the run, instead of the app failing after it ended | Validators count against output retries: keep checks deterministic and cheap; a check that needs a person stays outside the run | high | https://pydantic.dev/docs/ai/core-concepts/output/#output-validator-functions |
| S-UNTRUSTED-IN-INSTRUCTIONS | Untrusted text (emails, webhook payloads, retrieved documents, user-supplied files) pasted into `instructions` or the system prompt | f-strings or concatenation that put request data into `instructions=`, `system_prompt=` or `@agent.instructions` return values | Return it from a tool (2.0.0), or enqueue it as a `DataCapabilityPart` (2.70.0) | Puts the text in its author's voice, so text someone else wrote can't speak as the operator | Framing lowers the risk but isn't a security control: check important actions in code too. Facts your own code computed (dates, account status) belong in instructions | high | https://pydantic.dev/docs/ai/core-concepts/message-history/#injecting-messages-mid-run |
| S-TRUST-DEPS | Tenant, user or account ids that scope access passed as tool parameters the model fills | tool signatures with params like `user_id`, `tenant_id`, `account_id`, `org_id`, `partner_id` | Read them from `ctx.deps` (2.0.0) | The model can't widen its own scope by choosing another tenant's id | Only ids that decide what the caller may access; record ids the model picks within that scope (an invoice number) stay parameters | high | https://pydantic.dev/docs/ai/core-concepts/dependencies/ |
| S-APPROVAL | Approval handled in the app: a `pending_approval` column polled around runs, an `approve` tool the model can call, or an `approved: bool` argument the model sets | tools with `approved`/`confirmed` bool params; an approval tool exposed to the model; status polling around a run | `requires_approval=True` on the tool + `DeferredToolRequests` in `output_type` (2.0.0), resumed with `deferred_tool_results=`; or wait inside the run with `HandleDeferredToolCalls` (2.0.0) | The decision is collected outside the model, keyed on the tool call, and resumes the same conversation | The approver's identity comes from your app or deps, never from the model. While a call waits for approval, hold other input for that conversation | high | https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/ |
| S-DELEGATE-USAGE | A tool that runs another agent without passing the parent's usage, so the parent's limits never see the child's spend | `await <agent>.run(` or `.run_sync(` inside a tool body without `usage=` | Pass `usage=ctx.usage` and `usage_limits=...` to the delegate run (2.0.0), or use Harness `SubAgents` (pydantic-ai-harness 0.7.0), which forwards usage by default | One budget for the whole tree of agents | `SubAgents` hands the parent text, not a typed value: where the parent's code needs the typed result, keep agent-as-tool with `usage=ctx.usage` | high | https://pydantic.dev/docs/ai/guides/multi-agent-applications/ |
| S-LIMITS | Requests or tokens counted by hand with your own error at a threshold, or hook-based step counters that force an answer near the limit, or a run that hits `UsageLimitExceeded` and loses its work | counters on `result.usage()` compared to constants; custom "max steps" in hooks; `except UsageLimitExceeded` that retries with a higher limit | `UsageLimits(request_limit=..., total_tokens_limit=..., cost_limit=...)` (`cost_limit` 2.23.0); plus Harness `WrapUpAtLimits()` (pydantic-ai-harness 0.71.0) so the last allowed request produces the answer, with `wrapped_up_by(...)` telling your code it was cut short; without the harness, `capture_run_messages()` (2.0.0) keeps the messages of a run that hit the limit | Enforced before the request that would cross it, across delegated runs; the run ends with an answer instead of an exception | The default `request_limit` is a backstop, not a budget: set one deliberately. A wrapped-up answer may be partial: check `wrapped_up_by` before treating it as complete | high | https://pydantic.dev/docs/ai/core-concepts/agent/#usage-limits, https://pydantic.dev/docs/ai/harness/wrap-up-at-limits/ |
| S-RETRY-HTTP | Hand-written retry or backoff around model calls (tenacity or backoff decorators on functions that call `agent.run`, sleep loops on 429 or 5xx) | `@retry`, `tenacity`, `backoff` on functions calling `.run(`; `except ModelHTTPError` followed by `sleep` | Model settings `max_retries` and `request_timeout` (2.58.0), or the `pydantic_ai.retries` HTTP transports (2.0.0) | Retries one request rather than the whole run | `max_retries` only sets how many times the provider SDK retries, on the providers its docstring lists, and Google's client doesn't retry unless configured: elsewhere, use the `pydantic_ai.retries` transports, whose `wait_retry_after` honors `Retry-After`. Retry in one layer only: if a durable engine also retries, turn one of them off | high | https://pydantic.dev/docs/ai/core-concepts/retries/ |
| S-CACHE | Per-request data (timestamps, ids, user names) at the top of the instructions, and no prompt caching | dynamic values in the first instruction or system prompt; no `Caching` capability on agents that send long, repeated prefixes | `Caching` capability (2.55.0); keep static instructions first and per-request facts after them or in the prompt | Large cost and latency savings on repeated prefixes | Pays off only above the provider's minimum cacheable prefix and with repeated requests. A per-run value such as today's date in the first instruction breaks the prefix on every run: move it after the static text or into the prompt | medium | https://pydantic.dev/docs/ai/capabilities/caching/ |
| S-INSTRUMENT | Hand-written logging of prompts, responses and token counts | logging calls around `.run(` that dump messages, outputs or usage | `logfire.instrument_pydantic_ai()` or the `Instrumentation` capability (2.0.0), with `InstrumentationSettings(include_content=False)` (2.0.0) where content is sensitive | Full traces of model requests and tool calls with token counts and costs; content recording decided per agent | Decide what personal data may be recorded before turning content on; any OpenTelemetry backend works, not only Logfire | high | https://pydantic.dev/docs/ai/integrations/logfire/ |
