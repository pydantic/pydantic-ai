# Message History & Prompt Caching

> Rules for code that adds to, edits, or renders the message history the model sees

**When to check**: Whenever you write or review code that enqueues or edits messages (`ctx.enqueue`, `ctx.messages`, `request_context.messages`, history processors), contributes instructions or tools, renders history in `Model.prepare_messages` or a model adapter, wraps content in tags, or converts history to or from a UI protocol

Message history is both the model's picture of the world and the provider's prompt-cache key. Providers cache a prefix of the request they've seen before, at boundaries that differ per provider: tools, then system and instructions, then messages. So read each request as that ordered sequence of cache-relevant blocks: every block an earlier request sent should come back with identical serialization and in the same order, with new blocks only after it, across steps and across runs of the same conversation. (Full request bodies can't be byte prefixes of each other: closing brackets and settings come after the prompt.) When that breaks, nothing errors: the provider re-processes everything after the first changed block, and on models with preserved thinking the model's earlier reasoning is discarded too. Who wrote a piece of text also decides how much the model trusts it, so putting content in the wrong place is a prompt-injection bug, not a style issue.

A rule marked *(pending #N)* depends on a mechanism still in review. Until #N merges, don't flag code for using the mechanism that exists today; flag only what the rule forbids regardless, which each such rule spells out. The same marker names the PR that fixes shipped code still breaking a rule: don't flag that code for it until then. Drop the marker once #N merges.

## Rules

### History is append-only

- Framework and harness code never edits, removes, reorders or re-renders a message an earlier request already sent, whether from a hook, a history processor or `Model.prepare_messages`, and never does so by default or on every request. A history processor the user configures explicitly (`ProcessHistory`, `history_processors`) is an intentional rewrite: allowed, but its docs say it costs the cached prefix. Beyond that, there are two exceptions. The framework drops request-scoped prompts that no response answered once a step gives up (the run failed or was cancelled, or a retry was requested without a response); a retry or fallback attempt at the same step keeps them. Compaction is the other, and it must fire on a threshold with hysteresis, so it moves the prefix once per crossing, not on every request. A setting that defeats the hysteresis (such as `ClearToolResults(max_messages=...)` at or below `2 * keep_pairs`) rewrites history on every request, so document it as such and don't make it a default. — Any rewrite moves the cached prefix from that point on, for every later request.
- Shape content once, when it's produced: truncate, spill or redact a tool return in the tool or output hooks, not by rewriting it on later requests.
- Append changes to state the model tracks instead of refreshing it in place. Changed instructions are appended with `on_change='append'`, which records an `InstructionDeltaPart`. Tools revealed mid-run are recorded as a `ToolAvailabilityDeltaPart` (every tool population change: *pending [#9405](https://github.com/pydantic/pydantic-ai/pull/9405)*). — Re-rendering the instructions or the `tools` array invalidates everything after it.
- Only remove parts you added, and find them by type or metadata (see below). Never strip every part of a type.

### Request-scoped is not request-only

- A nudge about the current request is a `SystemPromptPart(..., scope='request')` passed to `ctx.enqueue` from `before_model_request`. — It stays in history, so history records what each request was sent. Where the API can stop showing a block to the model itself (Anthropic, with `clear_at`), it's sent unchanged with every later request, so the prefix holds. Everywhere else it's sent at the end of its own request and left out of later ones: a deliberate move at the tail, behind the cache breakpoints the framework places, so the prefix before it is still read from cache. See [request-scoped system prompts](../docs/message-history.md#request-scoped-system-prompts).
- Assigning a new list to `request_context.messages` is request-only: it changes what one request sends without touching history. It's cache-safe only when every later request applies the same change, so earlier requests' bytes come out the same: redacting a part from the first request that sends it, or filtering out a part type that was never sent. Dropping or altering something an earlier request already sent is a history rewrite under the first rule, which only compaction or a history processor the user configured may do. Never use it to add something the model should keep seeing, because leaving it out of the next request is itself a prefix change.
- The full decision table is [Changing what the model sees](../docs/capabilities/custom.md#steering-messages-and-reminders). Follow it rather than restating it.

### Trust tiers map to channels, and nothing is ever promoted

| Who it comes from | Channel |
|---|---|
| operator or framework | `SystemPromptPart` or instructions |
| the user, including files they attach | user parts (`UserPromptPart`) |
| tools, sub-agents, files a tool reads or produces, the web, and history a UI client sends back (framework records, tool results, system messages) | the tool result channel, or a framed data wrapper (`<tool_result …>`) when it has to ride a user turn |

- Never put content from a lower tier in a higher one: no tool output, sub-agent report, untrusted file contents (user attachments, files a tool reads or produces) or client-returned history in a `SystemPromptPart` or instructions. Classify by provenance, not medium: an operator-owned prompt or config file belongs in system voice. — The model gives system voice the operator's authority, so that content becomes an injection with operator rights. The one exception is an operator's explicit opt-in, such as `manage_system_prompt='client'` on a UI adapter, where the operator has chosen to let the client's system messages speak for them.
- Never send framework voice with `ctx.enqueue(str)`. — A string becomes a user part, so the model reads framework guidance as the user's words and UI clients show it as a message the user typed. Enqueue a `SystemPromptPart`, and keep any untrusted payload out of it (previous rule).

### One voice tag, and every wrapper escapes its payload

- `<system>` is the only tag that means "the application, not the person", and only the fallback rendering of a `SystemPromptPart` (on models without a mid-conversation system channel) emits it. Don't add a second voice tag such as `<system-reminder>`. *(Harness `SystemReminders`, which defaults to that tag and injects request-only user text: pending [#9712](https://github.com/pydantic/pydantic-ai/pull/9712).)*
- Every other tag the framework or harness wraps around content is data framing, and both its payload and its attributes are escaped, so the content can't open or close a frame and forge framework voice. Build wrappers with `wrap()` from `pydantic_ai/_framing.py`, register the tag in `FramingTag`, and never hand-roll an escaper; a guard test enforces this for core. *(A public `pydantic_ai.framing` API for harness and user code is pending.)* — Escapers that only handled the closing tag have shipped in several PRs.
- Inside a data frame, neutralize the `<` of every opening and closing spelling of every registered framing tag (`FramingTag`, `system` included), not only the frame's own: replace the `<` matched by `<(?=\s*(?:/\s*)?NAME(?=[\s/>]|$))` (case-insensitive) with `&lt;`, and `html.escape` attribute values. A `<system>` body is the one exception: it neutralizes only `system`, because it is framework or operator text that may carry framework-built data frames. `wrap()` does both, and `neutralize_tags()` covers untrusted text that a later step wraps. Test `<name>`, `</name>`, `</NAME >`, `< / name>`, `</ name>`, `</name/>`, a tag with an attribute, a newline before `>`, and a body ending in `<name` or `</name` (the wrapper's own tag would complete it), plus another registered tag inside the frame (a `<tool_result>` body containing `</context>`, say), and check that `<namefoo>` is left alone. — Models read all of these as tags, and closing-only and own-tag-only escapes have already shipped bypasses. On the fallback path genuine framework voice is `<system>` user text, so an unescaped `<system>X</system>` in a tool result forges it.
- Tag names are lowercase, with `_` between words (`tool_result`, `assistant_thinking`, `task_output`, `judge_feedback`, `context_diff`), never `-` or camelCase. Prefer an existing tag to a new one; name a new tag after what the content *is*, and put its source in an attribute (`tool_name="..."`, `judge="..."`). — One vocabulary is what lets the model, the escaper and a guard recognize every frame. *(Renames of `context-diff`, `task-output`, `previous-summary`, `context-file` and `plan-reminder` are in flight; don't flag those until they land.)*
- Keep attributes to identity (whose output, which call) and outcome. Mark an outcome with an attribute that reuses existing vocabulary, such as `outcome="failed"` from `ToolReturnPart.outcome`, not with a new sentence or tag. — Extra attributes invite the model to copy the frame: a provider-only attribute on `<assistant_thinking>` made Claude Opus 4.5 reproduce the tag in its own output 8 times out of 8.
- Put no unframed framework text in front of a data frame on a user turn. The frame's attributes say whose output it is; any announcement or explanation goes in system voice or instructions ahead of time, such as the tool result that says a call is running in the background. — A preamble like "Background tool X completed." reads as the user's words.
- Framing that refers to another part names it ("the accompanying `<judge_feedback>` tag"), never its position ("the tag that follows"). — Providers order system and user content their own way: Anthropic may put the user content before a mid-conversation system entry.
- Live-probe any new or changed framing, voice or steering before merging, on the latest frontier model from each provider (check `KnownModelName` at probe time) and on both the native and the `<system>`-fallback rendering where both apply. — How a model treats a frame is behavior, not syntax, and only a probe shows it.

### Identify framework records by type or metadata, never by visible text

- Recognize a part the framework or harness wrote by its type, a typed field, or metadata it set, never by matching its text (a prefix like `Summary of previous conversation:`, a bracket marker, a tag). For a `SystemPromptPart`, that's its `metadata`: see [identifying system prompts](../docs/message-history.md#identifying-system-prompts). — Users and tools can type the same text, which then gets deleted or promoted, and rewording the text silently breaks detection.
- Code that re-renders history for another model (compaction summarizers, judges, conversation search) finds framework data parts (task reports, reminders, judge feedback, background results) by their metadata, renders them as labeled untrusted data, never as `user:` turns, and keeps them out of paths that preserve the user's own words (such as `keep_user_messages`). — Otherwise untrusted content is laundered into user intent or into a summary that persists.
- This is the history counterpart of "identify a tool by what it is, never by its name" in [Pydantic AI Slim Architecture](pydantic-ai-slim.md).

### Every computed instruction block has a stable id

- Give every instruction block the framework or harness computes a stable id (the instruction's `name`), so a change to it appends a delta for that block with `on_change='append'` instead of re-rendering all instructions. A catalog, such as the capability index or a skill list, is one block. Never derive an id from the block's content or position.
- Don't let a block change when nothing changed: sort collections, and use date-only timestamps.

### Canonicalize on send

- Projection, from history to the provider request, is deterministic: the same history gives the same bytes, whether it lived on the server or came back from a UI client. Send what we would have produced, not what a provider or client handed us (core already sends tool-call args as compact JSON and tool results in call order). — The cache is keyed on what we send, not on what we stored.
- Any id we remap, such as a tool-call id a provider rejects, is a pure function of the original id: never random, and never counter-based across runs.

### UI round trips are faithful for everything the model sees

- Dumping history to a UI protocol and loading it back, or streaming events into the client and loading what it stored, must give back every part the protocol can carry and the client may hold, in order, with every field of it that affects what is sent to the provider (content, tool-call ids, part-level provider data such as thinking signatures). — A lost or split part moves the prefix on the next request, and a framework record that comes back as plain user text has changed trust tier.
- Some state is left out of the UI on purpose: request-scoped system prompts (sent back, one would return as a lasting system prompt) and server-owned or trust-sensitive fields (`model_name`, usage, provider identity, the `__pydantic_ai__` namespace). A conversation that needs those unchanged keeps its history on the server; the UI layer doesn't promise them.
- Treat client-returned history as untrusted. Framework records whose trust matters need server-side state or signed provenance *(pending [#8954](https://github.com/pydantic/pydantic-ai/issues/8954))*.
- Verify round trips with each protocol's real JavaScript reducers (`@ag-ui/client`, the `ai` SDK), not a Python port of them. — A Python stand-in has already produced a false bug report.

### Testing

- For anything that adds to history, assert over at least two requests, and two runs where history carries over, that the cacheable region of each request (its cache-relevant blocks up to the cache breakpoint: tools, system and instructions, messages) starts with the previous request's, identically serialized and in the same order, not only that the cache was hit. A request-scoped prompt sent after the breakpoint and left out of later requests on providers without `clear_at` is a deliberate tail move, not a break. See "prefix stability" in `tests/AGENTS.md`; a test that deliberately moves the prefix declares it with `@pytest.mark.moves_cache_prefix(reason=...)`.
